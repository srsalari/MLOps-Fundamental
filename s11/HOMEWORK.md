# تکلیف جلسه‌ی ۱۱

مهلت: پیش از شروع جلسه‌ی ۱۲. همه‌ی کارها روی یک شاخه‌ی تازه و با یک Pull Request وارد `main` شوند. بخش ۱ اختیاری است، ولی بخش‌های ۲ و ۳ لازم‌اند.

```bash
cd ~/work/churn-mlops && git switch main && git pull && git switch -c feature/homework-11
```

<bdi dir="rtl">cluster باید روشن باشد و `make k8s-deploy` در آن کار کند. در هر ترمینال تازه alias را دوباره بزنید و context را بررسی کنید (هرگز بدون `--context kind-mlops` به cluster دستور نزنید):</bdi>

```bash
alias k='kubectl --context kind-mlops'
```

```bash
kubectl config current-context
```

<bdi dir="rtl">MLflow هم باید روشن باشد. اگر pod‌ها را خراب کردید، `k apply -f k8s/` و `k -n churn rollout undo deployment/churn-api` راه برگشت‌اند.</bdi>

قاعده‌ی کلی تکلیف: هر تغییری که می‌دهید **در فایل‌های `k8s/` بنویسید و با `apply` اعمال کنید** (نه با `set` یا `edit` دستی)، تا Git منبع حقیقت بماند. هر عددی که می‌گویید باید با خروجی یک دستور واقعی ثابت شود.

## ۱. اختیاری: چهار replica و یک تغییر دیگر

یکی از این دو را انتخاب کنید:

- <bdi dir="rtl">`replicas` را به ۴ برسانید. چه تعداد pod دارید؟ چند ثانیه تا همه آماده می‌شوند؟ آیا cluster (یک node) جا دارد؟ (به `describe node` و بخش `Allocated resources` نگاه کنید.)</bdi>
- یک ConfigMap دوم برای `PREDICT_THRESHOLD` بسازید و Deployment را طوری تغییر دهید که آستانه از آن خوانده شود. بعد با ۰٫۹۰ و ۰٫۵۰ پیش‌بینی همان مشتری را مقایسه کنید.

برای هر کدام بنویسید: چه فایلی را عوض کردید، دستورها، و چه دیدید.

## ۲. تنظیم منابع و probe‌ها (لازم)

هدف: برای API یک **تنظیم مستند و اندازه‌گیری‌شده** پیدا کنید. به‌جای «حدس»، عدد با دستور.

### الف) پیدا کردن حافظه‌ی مناسب

۱. مصرف حافظه‌ی واقعی یک pod را وقتی بی‌کار است و بعد از چند ده درخواست `/predict` اندازه بگیرید. دستور و خروجی را بنویسید. (راهنما: اگر `k top pod` در cluster کار نکرد، مصرف را از داخل container بخوانید؛ فایل‌های `/sys/fs/cgroup/memory.current` یا `/sys/fs/cgroup/memory/memory.usage_in_bytes` را با `k exec` امتحان کنید. روشی را که کار کرد توضیح دهید.)

۲. <bdi dir="rtl">`limits.memory` را در `deployment.yaml` به چند مقدار مختلف کاهش دهید، هر بار `apply` کنید و صبر کنید تا نتیجه روشن شود. مقدار کم‌ترین حدی را پیدا کنید که pod هنوز بدون `OOMKilled` و بدون `RESTARTS` بالا می‌آید. برای هر مقدار بنویسید:</bdi>

| مقدار limit | pod آماده شد؟ | `RESTARTS` | `Last State` در `describe` |
| --- | --- | --- | --- |
| ... | ... | ... | ... |

۳. بعد از پیدا کردن آن حد، یک **حد امن** انتخاب کنید (چرا نه خود حد؟) و در فایل بگذارید. `requests.memory` را هم با دلیل تنظیم کنید. بنویسید چرا requests و limits را برابر یا نابرابر گذاشتید.

توجه: هر آزمایش شکست‌خورده را با `rollout undo` یا با اعمال دوباره‌ی فایل درست جمع کنید. در پایان cluster باید `2/2` سالم باشد.

### ب) startupProbe

برنامه بارگذاری مدل را فقط هنگام شروع انجام می‌دهد؛ اگر MLflow آهسته باشد، شروع طول می‌کشد. به `deployment.yaml` یک **startupProbe** اضافه کنید که:

- از `/ready` استفاده کند،
- به برنامه تا حدود ۶۰ ثانیه برای شروع فرصت بدهد،
- و تا وقتی startupProbe موفق نشده، liveness و readiness اجرا نشوند (این رفتار خود Kubernetes است؛ در مستندات چرایی را بخوانید و با یک جمله بنویسید).

سپس این را آزمایش کنید: MLflow را خاموش کنید، `rollout restart` بزنید و رفتار pod جدید را ببینید؛ دوباره MLflow را روشن کنید **و بدون کشتن pod دستی** ببینید چه می‌شود. مقدار `failureThreshold` و `periodSeconds` را طوری انتخاب کنید که حاصل‌ضربشان مقصود شما را بدهد. بنویسید:

- پیش از startupProbe، با MLflow خاموش، pod چه وضعیتی داشت (گام ۵ آزمایشگاه)؟ و حالا چه؟
- چرا این تغییر مشکل «pod برای همیشه ناآماده بماند» را حل می‌کند یا نمی‌کند؟ صادقانه بنویسید.

### ج) مشاهده‌ی یک rollout

یک تغییر بی‌خطر در Deployment بدهید (مثلاً `periodSeconds` در readiness یا یک label تازه روی pod template) و با `apply` اعمال کنید. در همان حال، در ترمینال دیگر این را اجرا کنید:

```bash
k -n churn get pods -w
```

(با Ctrl+C قطعش کنید.) از خروجی توضیح دهید:

- در طول rollout حداکثر چند pod با هم وجود داشت و چرا؟ (به `maxSurge` و `maxUnavailable` ربط دهید.)
- <bdi dir="rtl">ReplicaSet قدیمی چه شد؟ آیا حذف شد؟ با `k -n churn get rs` ببینید و بگویید چرا این برای rollback مهم است.</bdi>
- با `k -n churn rollout history` چند revision دارید؟ برای تغییر خودتان `change-cause` ثبت کنید.

## ۳. دو پاراگراف (لازم)

متن باید از خودتان باشد.

**پاراگراف اول** (چهار تا شش جمله): فرق pod، ReplicaSet، Deployment و Service را با یک مثال از همین جلسه بنویسید. اگر pod را با دست حذف کنیم چه کسی دوباره می‌سازد، و اگر Deployment را حذف کنیم چه می‌شود؟

**پاراگراف دوم** (چهار تا شش جمله): دلیل نیاز نداشتن این API به Secret را توضیح دهید. بعد بنویسید در چه شرایطی یک Secret لازم می‌شد، چه چیزی را در آن می‌گذاشتید، و چرا base64 حفاظت نیست.
