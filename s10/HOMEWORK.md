# تکلیف جلسه‌ی ۱۰

مهلت: پیش از شروع جلسه‌ی ۱۱. همه‌ی کارها روی یک شاخه‌ی تازه و با یک Pull Request وارد `main` شوند. بخش ۱ اختیاری است، ولی بخش‌های ۲ و ۳ لازم‌اند.

```bash
cd ~/work/churn-mlops && git switch main && git pull && git switch -c feature/homework-10
```

<bdi dir="rtl">VM تمرینی (`mlops-vm`) باید روشن باشد و `make deploy` در آن کار کند (`docker ps --filter name=mlops-vm`). MLflow هم باید روشن باشد.</bdi>

## ۱. اختیاری: یک تغییر در playbook

یک تغییر کوچک در `deploy/templates/churn-api.logrotate.j2` یا `deploy/deploy.yml` بدهید، به‌طوری که تأثیر آن را بتوانید ببینید. چند نمونه (یکی را انتخاب کنید):

- نگه‌داری لاگ‌ها را از ۷ به ۱۴ نسخه ببرید (متغیر را در `vars` تعریف کنید، نه عدد ثابت در قالب).
- یک متغیر تازه برای `proxy_read_timeout` Nginx بسازید.

سپس این‌ها را انجام دهید و نتیجه را بنویسید:

1. اجرای آزمایشی (`--check --diff`) را بزنید و تفاوتی را که Ansible نشان داد یادداشت کنید.
2. <bdi dir="rtl">`make deploy` را بزنید و در `PLAY RECAP` ببینید چند task تغییر کرد.</bdi>
3. دوباره `make deploy` بزنید و بنویسید `changed` چند شد و چرا.

## ۲. مستندسازی سناریوی rollback

سناریو: امروز صبح مدل جدید (`@champion` تازه) را مستقر کردید. نیم ساعت بعد گزارش می‌رسد که پیش‌بینی‌ها عجیب شده‌اند. ساعت آخر شب است و شما نیستید؛ همکار شما فقط `RUNBOOK.md` را دارد.

۱. فایل `RUNBOOK.md` پروژه را کامل و بازنویسی کنید تا بخش **Rollback** آن این‌ها را روشن بگوید:

| پرسش | چه چیزی باید در سند باشد |
| --- | --- |
| چطور بفهمم کدام نسخه‌ی مدل الان سرویس می‌دهد؟ | دستور و جای خروجی |
| چطور به نسخه‌ی قبلی برگردم؟ | دستور دقیق، و اینکه چقدر طول می‌کشد و چه چیزی restart می‌شود |
| چطور مطمئن شوم برگشت کامل شد؟ | دستور بررسی و نتیجه‌ی مورد انتظار |
| اگر rollback خودش شکست خورد چه کنم؟ | حداقل دو علت محتمل و کجا باید نگاه کرد (لاگ‌ها) |
| چطور دوباره به جلو برگردم؟ | دستور، و اینکه چه موقع این کار درست است |

۲. سند را **واقعاً امتحان کنید**: خودتان فقط از روی `RUNBOOK.md` (بدون نگاه کردن به README) rollback کنید و جلو بیایید. هر جایی که گیر کردید یا دستور کم بود، همان‌جا سند را درست کنید.

۳. بخش‌های دیگر سند (Service overview، Start/stop، Check health، Logs، Who to call) هم باید پر باشند و هیچ `...` در آن نماند.

۴. در انتهای سند یک بخش کوتاه به نام «Known limits» اضافه کنید و صادقانه بنویسید این روش استقرار چه محدودیت‌هایی دارد. به این‌ها فکر کنید: چند سرویس با هم؟ نیاز به downtime؟ چه کسی به VM دسترسی دارد؟ اگر خود VM بمیرد چه می‌شود؟

## ۳. یک پاراگراف

در یک پاراگراف کوتاه (پنج تا هشت جمله) بنویسید:

- <bdi dir="rtl">Ansible با یک اسکریپت `bash` که همین دستورها را پشت سر هم می‌زند چه فرقی دارد؟ (به idempotency و `--check` فکر کنید.)</bdi>
- کار Terraform چیست و چرا آن را جای Ansible (یا Ansible را جای آن) نگذاشتیم؟
- در چه موقعیتی استقرار روی VM را به Kubernetes ترجیح می‌دهید و در چه موقعیتی برعکس؟

متن باید از خودتان باشد.

## ۴. commit و push

```bash
git add RUNBOOK.md deploy && git commit -m "docs: rollback runbook and homework 10"
```

اگر بخش ۱ را انجام نداده‌اید و پوشه‌ی `deploy` تغییری نکرده، نام آن را از دستور حذف کنید.

```bash
git push -u origin feature/homework-10
```

در Gitea Pull Request بسازید و Merge کنید، بعد:

```bash
git switch main && git pull
```

## برای مدرس بفرستید


2. فایل `RUNBOOK.md` نهایی

4. پاراگراف بخش ۳
5. اگر بخش ۱ را انجام دادید: تفاوت `--check --diff`، خلاصه‌ی `PLAY RECAP` اجرای اول و دوم، و توضیح
