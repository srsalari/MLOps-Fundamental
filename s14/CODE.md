# توضیح کد جلسه‌ی ۱۴

در این جلسه کد مدل و API تغییر نمی‌کند. فایل‌های تازه سه دسته‌اند: اسکریپت امتیازدهی، سندها (Runbook، README، Demo) و دو هدف Makefile.

فایل‌های این جلسه:

- `scripts/readiness_check.sh`: اسکریپت امتیازدهی (گام ۴).
- `PRODUCTION-READINESS.md`: فهرست ۳۴ آیتم با امتیاز و دستور بررسی دستی (فقط خواندنی).
- `RUNBOOK.md`، `README.project.md` (می‌شود `README.md` پروژه) و `DEMO.md`: قالب سندها (گام ۵).
- `STORYTELLING.md`: راهنمای Demo و رزومه (فقط خواندنی).
- `Makefile`: هدف‌های `demo-check` و `readiness` به آخر Makefile جلسه‌ی ۱۳ اضافه شده‌اند.
- `preflight.sh`: بررسی آمادگی پیش از کلاس (کد آموزشی نیست).

کامنت‌های داخل فایل‌ها عمداً انگلیسی‌اند؛ شرح فارسی در همین فایل است.

## `scripts/readiness_check.sh`

یک اسکریپت bash که پروژه را با چک‌لیست می‌سنجد. فقط می‌خواند و چیزی را عوض نمی‌کند. ساختارش سه بخش است:

۱. **تنظیمات** در ابتدا: آدرس سرویس‌ها از متغیرهای محیطی می‌آید و پیش‌فرض‌ها مقدار کلاس‌اند (مثلاً `SERVICE_URL`، `KCTX`، `TAG`). به همین دلیل روی لپ‌تاپ هر دانشجو بدون تغییر کار می‌کند.

۲. **تابع‌های بررسی** که نامشان با `c_` شروع می‌شود. هر تابع یک آیتم را می‌سنجد و با کد برگشتی جواب می‌دهد:

| کد برگشتی | معنی |
|---|---|
| `0` | برقرار است (PASS) |
| `1` | برقرار نیست (FAIL) |
| `77` | سنجیده نشد (SKIP): مثلاً رمز Gitea نداده‌اید یا `QUICK=1` زده‌اید |

یک نمونه ساده:

```bash
c_dockerfile() { [ "$(grep -c '^FROM ' Dockerfile)" -ge 2 ] && grep -q '^USER ' Dockerfile && grep -q '^HEALTHCHECK' Dockerfile; }
```

یعنی: Dockerfile حداقل دو `FROM` (دو مرحله) و یک `USER` و یک `HEALTHCHECK` دارد. عملگر `&&` یعنی هر سه باید درست باشند.

۳. **موتور** و فهرست آیتم‌ها: تابع `item` این‌ها را می‌گیرد: کد آیتم، امتیاز، جلسه‌ها، نام تابع، توضیح و «چطور درست کنم». تابع را اجرا می‌کند، نتیجه را چاپ می‌کند و امتیاز را جمع می‌زند:

```bash
item S3 3 9 c_dockerfile "Dockerfile: 2 stages, non-root USER, HEALTHCHECK" "s09/README.md step 2"
```

در پایان امتیاز کل، امتیازهای سنجیده‌نشده، آیتم‌های قرمز و یک «حکم» چاپ می‌شود و خط آخر `SCORE=97/100` است (برای خواندن ماشینی توسط `verify.sh`). کد خروج `0` یعنی امتیاز ۸۰ یا بیشتر.

چند نکته‌ی فنی که بد نیست بدانید:

| بخش کد | چرا این‌طور است |
|---|---|
| `git grep -F -e "$sec"` در آیتم R2 | رمز S3 را در همه‌ی فایل‌های ردیابی‌شده و در همه‌ی تاریخچه‌ی Git جست‌وجو می‌کند. رمز هرگز چاپ نمی‌شود |
| `helm template ... \| grep readinessProbe` در D2 | chart را بدون cluster به YAML تبدیل می‌کند و ببیند probe و resources در خروجی هست |
| `curl -u "$GU:$GP"` در O2 | API اجراهای Actions در Gitea حتی برای مخزن عمومی رمز می‌خواهد (جلسه‌ی ۱۳) |
| `local` در توابع | متغیر فقط داخل تابع می‌ماند و روی بقیه اثر نمی‌گذارد |
| `set -uo pipefail` | متغیر تعریف‌نشده خطا می‌شود و خطای وسط pipe گم نمی‌شود. `-e` را عمداً نگذاشته‌ایم: بررسی‌ها باید شکست بخورند و اسکریپت ادامه بدهد |

## `Makefile` (دو هدف تازه)

```make
demo-check:
	@curl -fsS --max-time 5 $(SERVICE_URL)/ready ...
	@QUICK=1 scripts/readiness_check.sh | tail -8
```

`demo-check` سه آدرس را (سرویس، Prometheus، Grafana) با `curl` می‌پرسد و امتیاز سریع را نشان می‌دهد (`QUICK=1` یعنی pytest و Trivy را رد کن؛ حدود ۱۰ ثانیه). علامت `@` اول خط یعنی خود دستور چاپ نشود، فقط خروجی‌اش. هدف `readiness` امتیاز کامل می‌دهد.

## سندها

`RUNBOOK.md` فایل «بدون فکر کردن اجرا کن» است: هر بخش (Start، Health check، Stop، Restart، Logs، Rollback) فقط دستورهای واقعی این پروژه را دارد. جای‌نگهدارها (علامت کوچک‌تر، کلمه‌ی FILL، دو نقطه و یک راهنما) جاهایی‌اند که فقط شما می‌دانید (مسئول، SLO، حادثه‌ی خودتان). `README.project.md` صفحه‌ی اول مخزن است؛ `DEMO.md` متن زمان‌دار Demo است. اسکریپت `readiness_check.sh` وجود بخش‌های لازم و نبودن جای‌نگهدار را می‌سنجد.
