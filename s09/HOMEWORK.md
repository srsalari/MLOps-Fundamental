# تکلیف جلسه‌ی ۹

مهلت: پیش از شروع جلسه‌ی ۱۰. همه‌ی کارها روی یک شاخه‌ی تازه و با یک Pull Request وارد `main` شوند. بخش ۱ اختیاری است، ولی بخش‌های ۲ و ۳ لازم‌اند.

```bash
cd ~/work/churn-mlops && git switch main && git pull && git switch -c feature/homework-9
```

<bdi dir="rtl">image `churn-api:0.7.0` باید روی دستگاه شما ساخته شده باشد (`docker images churn-api`) و پایگاه Trivy روی دیسک باشد.</bdi>

## ۱. اختیاری: SBOM با Syft

*<bdi dir="rtl">*SBOM** (فهرست مواد نرم‌افزار) فهرست همه‌ی پکیج‌هایی است که داخل یک image هست. ابزار Syft آن را می‌سازد.</bdi>

```bash
syft --version
```

یک SBOM از image بسازید (فرمت SPDX JSON) و فایل را کنار پروژه نگه دارید (لازم نیست commit شود، چون حدود 3.5MB است):

```bash
syft -q churn-api:0.7.0 -o spdx-json=sbom.spdx.json
```

سپس این‌ها را بررسی کنید و به زبان خودتان بنویسید:

- چند پکیج در SBOM هست و از چه نوع‌هایی (پکیج‌های Debian و پکیج‌های Python)؟
- نسخه‌ی سه پکیج را که خودتان انتخاب می‌کنید از SBOM پیدا کنید (مثلاً `fastapi`، `mlflow`، `pillow`) و با `uv.lock` مقایسه کنید.
- خود SBOM را با Trivy اسکن کنید (`trivy sbom ...` با گزینه‌های `--skip-db-update --offline-scan`) و نتیجه را با `trivy image` روی خود image مقایسه کنید. تفاوت را ببینید و بنویسید چرا فکر می‌کنید پیش آمد، و برای دروازه‌ی کیفیت کدام را انتخاب می‌کنید.
- همین کار را با فرمت CycloneDX (`-o cyclonedx-json=...`) هم امتحان کنید و بنویسید فرقی دیدید یا نه.

اگر Syft نصب نیست، بخش اختیاری را رها کنید و پایین بنویسید که نصب نبود.

## ۲. مستندسازی موارد باقی‌مانده

در جلسه، ۶۳ مورد Debian ماند که اصلاح ندارد. شما باید ریسک را **آگاهانه** ثبت کنید، نه نادیده بگیرید.

۱. فهرست موارد HIGH و CRITICAL را بدون `--ignore-unfixed` بگیرید (برای مثال در قالب JSON یا جدول) و آن را برای خودتان نگاه کنید.

۲. حداقل **سه مورد** انتخاب کنید که به نظر شما مهم‌ترند یا جالب‌اند. برای هر مورد این‌ها را بنویسید:

| ستون | توضیح |
| --- | --- |
| شناسه | CVE و نام پکیج و نسخه‌ی نصب‌شده |
| وضعیت | `affected` یا `will_not_fix` یا چیز دیگر |
| ریسک در این سرویس | این پکیج در سرویس ما واقعاً استفاده می‌شود؟ ورودی کاربر به آن می‌رسد؟ (در حد یکی دو جمله) |
| تصمیم | فعلاً می‌پذیریم / base image را عوض می‌کنیم / ... و تا کی بازبینی می‌کنیم |

۳. دو راه برای ثبت دارید و یکی را انتخاب کنید (یا هر دو):

- فایل `SECURITY.md` در ریشه‌ی پروژه با جدول بالا؛
- فایل `.trivyignore` که در آن هر CVE در یک خط است و **بالای هر خط یک کامنت (دلیل)** دارد.

۴. اگر `.trivyignore` را انتخاب کردید، بررسی کنید که `trivy image` (با همان گزینه‌های `make scan`، به‌علاوه‌ی فایل ignore) آن موارد را دیگر نشان نمی‌دهد، و بنویسید چه فرقی بین «نادیده گرفتن با دلیل» و «ندیدن» هست.

## ۳. یک پاراگراف

در یک پاراگراف کوتاه (پنج تا هشت جمله) بنویسید:

- در این جلسه سه کار برای امن‌تر شدن image کردیم (چند مرحله‌ای بودن، کاربر غیر root، `.dockerignore`). از این سه کار، هر کدام جلوی چه خطری را می‌گیرد؟
- چرا اسکن Trivy به‌تنهایی کافی نیست؟ (به یافته‌ی آزمایش با فایل `.env` فکر کنید.)
- کجا تصمیم می‌گیرید اسکن را «دروازه» کنید که با آسیب‌پذیری قابل‌رفع شکست بخورد، و کجا نه؟

متن باید از خودتان باشد.

## ۴. commit و push

فایل SBOM نباید وارد Git شود. اگر بخش ۱ را انجام دادید، اول آن را به `.gitignore` اضافه کنید:

```bash
echo 'sbom*.json' >> .gitignore
```

بعد فقط فایل‌های خودتان را commit کنید (هر کدام را که ساخته‌اید):

```bash
git add .gitignore SECURITY.md .trivyignore && git commit -m "docs: security notes and homework 9"
```

اگر یکی از دو فایل را نساخته‌اید، نامش را از دستور `git add` حذف کنید.

```bash
git push -u origin feature/homework-9
```

در Gitea Pull Request بسازید و Merge کنید، بعد:

```bash
git switch main && git pull
```

## برای مدرس بفرستید

1. خروجی این دستور:

```bash
~/mlops-lab/scripts/verify.sh s09
```

2. خروجی `make scan` روی image نهایی
3. فایل `SECURITY.md` یا `.trivyignore` (با دلیل برای هر مورد)
4. پاراگراف بخش ۳
5. اگر بخش ۱ را انجام دادید: تعداد پکیج‌های SBOM، نسخه‌ی سه پکیجی که پیدا کردید، و توضیح مقایسه‌ی `trivy sbom` با `trivy image`
